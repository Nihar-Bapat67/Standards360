The problem

A tender is only as good as the standards it names

  • The officer drafting it is an engineer or a stores officer, not a standards expert
  • Scopes overlap, revisions are frequent, and allied standards are buried inside Clause 2 of each document
  • So today they copy last year's tender, ask a senior, or ask the vendor
  • The result is omitted standards, outdated citations and incomplete requirements — which becomes disputes, rejected bids and poor quality

Who uses it

Two people, two questions, one engine

  • Procurement official: which standards must I cite, and are my citations current?
  • Manufacturer: which standards must my product comply with, and what licence do I need?
  • Identical facts reach both. Only the wording in D2 and the template in D3 differ
  • Which is why the second persona costs about one extra day. Build them in sequence, never in parallel

Input

Five real situations, one pipeline

  • All five route through the same modules. What changes is which ones do the work
  • S2 is our strongest demo. It is how procurement actually works today, and judging someone's existing citations is far more impressive than answering a blank query
  • S5 shapes the interface. A system that asks a clarifying question needs somewhere to ask it — which is why intake is chat-shaped
  • Conversation in, document out. Not a chatbot: an intake interview that ends in a deliverable

How it is organised

The letter is the stage, the number is the position

  • C3 means the third module of the find-and-check stage. That is the whole naming scheme
  • A runs offline, before any user arrives, and produces files
  • B, C and D run per request and only read those files
  • The two halves share no code path and meet only at the stores. So the corpus can be rebuilt while the service answers — and the demo runs with no internet

Stage A · Developer 1

Build the knowledge base once

  • A1 collects metadata for all ~22,689 standards — status, supersession, amendments — plus the QCO list and the recognised-lab list
  • A2 splits each PDF into numbered clauses, not arbitrary chunks, so we can later quote the exact clause that justified a recommendation
  • A3 reads Clause 2 and records typed relationships — test method, terminology, safety, installation. This is the module no competing system has
  • A4 builds the two search indexes and the lookup table
  • This starts on Day 1. It is also the biggest risk, so the data spike happens before any model code

Stage B · Person 1

Understand what actually arrived

  • B3 uses an LLM with a fixed JSON schema, not a trained NER model. In ten days prompting beats training, and the schema keeps output machine-readable
  • B4 is the S2 demo. "Three of your five citations are fine, one is superseded, one belongs to a different product, and you are missing two test methods"
  • B5 never guesses. A per-category table says cement needs grade and application; LED needs wattage, IP rating and mounting
  • Everything below B5 receives a requirement object it can trust, which is why no later module has to hedge

Stage C · Person 2

C1 — narrow fifty thousand down to three

  • C1.1 builds a clean query from B3's fields and drops quantity and delivery terms, which only pull the search toward clauses mentioning tonnage
  • C1.6 takes the maximum clause score, never the mean. One perfect scope clause beats forty irrelevant test-procedure clauses in the same document
  • This stack is public prior art with published results. Get it working by Day 4 and then leave it alone
  • It is one module out of nineteen. The other eighteen are what make the answer trustworthy

Stage C · the differentiator

C2 — allied standards are a traversal, not a search

  • C2.1 expands only from seeds above 0.80. A weak seed turns one mistake into five
  • C2.3 goes two hops with a 0.5 decay, then stops. Hop three routinely pulls in a hundred unrelated standards
  • C2.4 weights by relation type, so test methods outrank related products
  • Every edge carries the clause it came from, which is the audit trail an auditor would ask for
  • A similarity search cannot compute this. A transitive closure is not a nearest-neighbour query

Stage C · no machine learning here

C3 and C4 — is it current, and is it legal

  • C3.1 normalises identifiers first. Tenders write IS 269, IS-269, IS 269 : 2015, I.S. 269. Everything downstream depends on this and it is the step teams skip
  • C3.3 follows supersession chains to the end, because a withdrawn standard can point at another that was itself later merged
  • C4 only needs the product category, so fire it at the same instant as C1. The certification panel is ready before the standards are
  • Both are database lookups and date comparisons. That is precisely why they are reliable

Stage C · drives B5 and every number shown

C5 — say how sure we are, honestly

  • A raw similarity score is not a probability. Showing one to a government user as though it were is dishonest
  • s2 is the signal most teams omit and the most informative one. 0.94 against 0.93 means we are guessing between two standards; 0.94 against 0.62 is decisive
  • Bands: high ≥ 0.75, medium 0.50–0.75, low below. B5 asks a question below 0.60 or when a required field is missing
  • Weights are starting points. Tune them on the fifty-pair gold set and write down what you chose

D2 · the part that is easy to misread

Three depths, not three guesses

  • Every depth names the same primary standard, with identical confidence and identical evidence
  • What changes is how many allied standards travel with it
  • That is a policy question about the tender — a five lakh purchase or a fifty crore one — not uncertainty in the engine
  • Build it as a slider or a cite-less / cite-more toggle. Three cards side by side reads as "the system is not sure"

Prior art · BIS-COMPASS

The finished parts are the parts that were never the differentiator

  • It reports Hit@3 100%, MRR@5 0.93 at 0.45 seconds on 559 standards. Flat retrieval is a solved, commoditised problem
  • Absent entirely: version resolution, QCO, citation validation, the sufficiency gate, allied-standard output, PDF generation, two personas
  • Its xref.py does extract citations, but only as a ranking tie-breaker capped at 0.025. They never reach the user
  • It has no licence file, so we cannot copy the code. We use the same public models and cite it as prior art, which is a strength in a pitch

Scope

Freeze this on Day 3 and stop arguing

We are building

  • All nineteen modules except the chatbot
  • All five input scenarios, both output modes
  • Two sectors only — cement and construction materials, plus one electrical category
  • Catalogue metadata for all ~22,689 standards
  • Procurement persona complete, manufacturer as a second template

We are not building

  • In-place PDF editing beyond the annexure
  • The remaining sectors, OCR for scanned standards
  • Restrictive-specification detection
  • Reverse-reference impact analysis
  • Live tender-portal scraping, accounts and history
  • Fine-tuning any model — no time, no data, no benefit

two sectors done properly beats eight done shallowly · the "not building" list is binding, not advisory

Tomorrow morning

Three things before anything else

01

Prove the data

One standard end to end: PDF in, clauses out, Clause 2 references extracted, one row in the database. If this is hard, the project changes shape and we need to know on Day 1, not Day 6.

02

Write the gold set

Fifty hand-written pairs of product description and the standard that is actually correct. Without it, nobody can tell whether a change improved anything and every argument becomes opinion.

03

Freeze the contracts

Every module's input and output shape, committed with fake fixture data. This is the single thing that lets five people build nineteen modules at the same time.
